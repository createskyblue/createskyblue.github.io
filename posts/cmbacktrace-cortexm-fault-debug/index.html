CmBacktrace 可以把 Cortex-M 的 HardFault 现场打印出来

CmBacktrace 是一个面向 ARM Cortex-M MCU 的错误追踪库。它主要解决一个常见调试痛点：设备发生 HardFault、BusFault、UsageFault 或断言失败后，现场信息很快丢失，只靠“程序死了”很难判断是哪一层函数触发了异常。

它的工作方式很直接：故障发生时，库从异常现场读取寄存器、栈指针和调用栈地址，把故障原因、固件信息、栈内容和调用链地址打印出来。拿到这些地址后，再配合 addr2line 和带调试信息的可执行文件，就可以把地址还原成函数名和源码行号。

它能解决什么

在 Cortex-M 项目里，HardFault 经常来自这些情况：

  • 空指针或野指针访问。
  • 未对齐访问。
  • 除零。
  • 访问非法地址。
  • 栈溢出或任务栈配置过小。
  • 中断或任务里触发断言。

没有工具时，常见做法是接上调试器、停在异常入口、手动看寄存器和汇编调用关系。问题偶发、现场设备不能接仿真器、故障后自动复位时，这种方法很难稳定复现。

CmBacktrace 的价值在于把异常现场变成可保存、可复制、可离线分析的日志。串口能打印就可以看到诊断信息；如果项目有 Flash 日志，也可以把故障信息保存下来，设备重启后再读取。

输出信息包含哪些内容

CmBacktrace 的输出通常围绕几类信息展开：

  • 固件名称、硬件版本、软件版本。
  • 故障类型和原因分析。
  • 异常现场寄存器。
  • 主栈或线程栈信息。
  • 调用栈地址。
  • 可选的栈内容 dump。

这些信息里，调用栈地址最适合定位源码。日志里只能看到地址时，还需要把地址交给 addr2line 转换。转换依赖编译产物中的符号信息，所以发布调试固件时要保留可用于定位的 ELF、OUT 或 AXF 文件。

先理解堆和栈

理解 CmBacktrace 前，需要先分清堆和栈。

栈是函数调用使用的一块连续内存。函数被调用时，CPU 和编译器会把返回地址、部分寄存器、局部变量、临时变量等内容放到栈里。这个函数运行结束后，它占用的栈空间会被释放，程序回到调用它的位置继续执行。

堆是动态内存分配使用的区域。malloc()、calloc()、new 这类接口通常从堆里申请空间，释放时再调用 free() 或 delete。堆上的数据生命周期由程序控制，适合存放运行期间才知道大小、需要跨函数继续使用的数据。

栈 stack
跟随函数调用自动增长和回收。保存返回地址、寄存器、参数、局部变量。空间通常提前固定，溢出后容易破坏返回路径。
堆 heap
由动态内存分配器管理。对象生命周期由申请和释放决定。常见风险是泄漏、碎片、越界写和释放后继续使用。

嵌入式项目里，栈空间通常在链接脚本或启动文件里提前固定好。裸机程序一般有主栈；RTOS 程序通常每个任务都有自己的任务栈。栈空间太小，函数调用层级太深，或者局部数组太大，都可能把栈撑爆。栈溢出后，轻则变量被踩坏，重则返回地址被破坏，程序跳到错误地址并触发 HardFault。

递归会持续消耗栈空间。每递归调用一次，都会产生一层新的函数栈帧；这一层会保存自己的参数、局部变量和返回地址。递归深度越大，栈帧叠得越多。递归没有正确退出条件，或者输入数据让递归层数超过预期，就会很快耗尽栈空间。

递归调用时的栈帧叠加
第 4 层递归：参数、局部变量、返回地址
第 3 层递归：参数、局部变量、返回地址
第 2 层递归：参数、局部变量、返回地址
第 1 层调用：参数、局部变量、返回地址
栈底：任务栈或主栈的固定边界
每多一层递归，都会新增一层栈帧。栈帧继续向固定边界外增长时，返回地址和相邻内存就可能被覆盖。

调用栈表示函数逐层调用形成的栈帧链。CmBacktrace 打印调用栈，本质上是在崩溃后从 SP 指向的栈空间里寻找返回地址，尽量还原故障发生前的函数调用路径。

它的实现原理

CmBacktrace 的原理可以分成三层：先确定代码段和栈范围，再从异常现场取出硬件保存的寄存器，最后在栈里寻找可能的返回地址。

初始化时，cm_backtrace_init() 会记录固件名、硬件版本和软件版本，同时从编译器或链接脚本导出的符号里读取主栈范围和代码段范围。Keil、IAR、GCC 的符号写法不同，所以库里分别处理了 STACK、CSTACK、_sstack、_estack、代码段起止地址这些信息。后面判断某个数值是否落在代码区，就依赖这个代码段范围。

Cortex-M 进入异常时，硬件会自动把一组寄存器压到当前栈里，包括 R0、R1、R2、R3、R12、LR、PC 和 xPSR。CmBacktrace 的 HardFault 汇编入口负责把异常时的 LR 和 SP 传给 cm_backtrace_fault()。库再按固定顺序从这段自动压栈帧里读出寄存器。

其中 PC 是异常发生时正在执行或即将执行的指令地址，通常是最直接的故障点。LR 是当前函数返回后要去的位置，可以帮助补出上一层调用关系。Cortex-M 使用 Thumb 指令集，函数地址最低位常带有 Thumb 状态标志，所以库在分析 LR/PC 时会做减 1 或减一个字长的修正，让地址落回真实指令附近。

调用栈回溯没有完整运行时元数据可用时，只能从栈里做启发式扫描。CmBacktrace 会从当前 SP 向栈顶遍历，把栈里的 32 位数当成潜在返回地址检查：地址要落在代码段范围内，Thumb 地址形态要合理，前一条指令还要像 BL 或 BLX 调用指令。通过这些条件过滤后，剩下的地址就组成打印出来的调用栈。

这也解释了调用栈偶尔不完整的原因。编译优化、尾调用、内联、栈损坏、栈溢出、手写汇编和异常发生位置都会影响栈上的返回地址形态。CmBacktrace 能显著提高定位效率，但它打印的是“基于异常现场和栈内容推导出来的调用链”，需要结合源码和 fault 类型一起判断。

崩溃日志里的地址是什么意思

崩溃日志里常见的地址可以分成三类。

第一类是寄存器地址。PC 指向异常现场的执行位置，优先拿它定位故障行。LR 指向返回地址，通常能说明当前函数由谁调用。R0 到 R3 常用于传参，遇到空指针、非法地址访问时，这些寄存器里可能能看到可疑指针。

第二类是 fault 状态寄存器。HFSR、CFSR 拆分出的 MFSR、BFSR、UFSR，以及 MMAR、BFAR 这类 fault address register，用来说明故障类别和访问地址。例如精确总线错误、非法状态、除零、未对齐访问等，会在不同 bit 上留下原因。

第三类是调用栈地址。CmBacktrace 打印的 call stack 是一串代码区地址，代表库推导出的调用路径。地址越靠前，通常越接近故障现场；后面的地址表示更上层的调用者。这些地址需要用 addr2line 继续解析成源码行号。

基本移植路径

移植时先把库文件加入工程：

  • cm_backtrace/cm_backtrace.c
  • cm_backtrace/cm_backtrace.h
  • cm_backtrace/cmb_def.h
  • 项目自己的 cmb_cfg.h
  • 对应编译器的 fault_handler 汇编文件，可选但推荐新项目优先使用

cmb_cfg.h 是移植的核心。最少要配置日志输出、平台类型和 CPU 类型：

#define cmb_println(...) printf(__VA_ARGS__); printf("\r\n")
#define CMB_USING_BARE_METAL_PLATFORM
#define CMB_CPU_PLATFORM_TYPE CMB_CPU_ARM_CORTEX_M3
#define CMB_USING_DUMP_STACK_INFO
#define CMB_PRINT_LANGUAGE CMB_PRINT_LANGUAGE_CHINESE_UTF8

如果项目运行 RTOS，则改成 CMB_USING_OS_PLATFORM，并配置 CMB_OS_PLATFORM_TYPE。仓库里提供了 RT-Thread、UCOS、FreeRTOS 的 demo，可以先找接近的工程参考。

初始化一般放在 BSP 和串口可用之后：

cm_backtrace_init("firmware_name", "hardware_v1.0", "software_v0.1");

这三个字符串会出现在故障日志里，适合写入固件名、硬件版本和软件版本。量产设备排查问题时，这些信息能避免拿错固件和硬件版本。

HardFault 入口怎么接

CmBacktrace 提供两种接入方式。

第一种是使用库里的 cmb_fault.S。它会定义 HardFault_Handler，准备好 LR 和 SP 后调用 cm_backtrace_fault()。这种方式对新项目更稳，因为异常入口的寄存器取值由汇编完成，手写错误的概率低。

使用这种方式时，项目里原有的 HardFault_Handler 要移除或注释掉，否则会出现重复定义。

第二种是在已有的 HardFault 入口里手动调用：

void cm_backtrace_fault(uint32_t fault_handler_lr, uint32_t fault_handler_sp);

这种方式需要自己保证传入的 LR 和 SP 是异常现场对应的值。传错以后，库仍然会运行，但调用栈和故障分析可能失真。

断言也可以接入

除了硬件 fault，CmBacktrace 也能记录断言失败：

cm_backtrace_assert(cmb_get_sp());

断言里获取 SP 的位置要尽量靠近断言入口。README 里特别提醒，如果在断言钩子的子函数里再取 SP，函数嵌套已经改变了栈现场，可能需要人为修正偏移。实际工程里更推荐在断言入口处直接调用，减少人为修正。

用 addr2line 还原源码位置

CmBacktrace 打印出的调用栈通常是一串地址。定位源码时，把这些地址交给 addr2line：

addr2line -e firmware.elf -a -f 08000a60 08000141 0800313f

常用参数含义：

  • -e 指定带符号信息的可执行文件。
  • -a 输出地址。
  • -f 输出函数名。

addr2line 属于 GNU Binutils。它做的事情是读取可执行文件里的符号表和 DWARF 调试信息，把一个机器地址映射回函数名、源文件路径和行号。符号表能告诉它地址落在哪个函数范围内，调试行号表能告诉它这个地址对应哪一行源码。

如果编译器生成的是 .axf 或 .out，也可以用对应文件作为 -e 的输入。关键是这个文件必须和设备正在运行的固件一致，并且保留调试符号。固件重新链接后，即使源码没改，函数地址也可能变化；拿错构建产物会得到错误的函数名和行号。

学习这个库时要抓住的边界

CmBacktrace 负责采集和打印异常现场。fault 修复、系统级日志、看门狗和崩溃后恢复策略仍然属于应用工程职责。工程里仍然要考虑故障日志保存、复位策略、版本匹配和现场数据回传。

它对栈信息很敏感。主栈名称、链接脚本里的栈符号、RTOS 任务栈获取方式都会影响调用栈结果。初始化时如果提示无法获取主栈，要先检查 cmb_cfg.h 里的栈配置和启动文件、链接脚本是否匹配。

FreeRTOS 场景还需要注意仓库文档里的提示：部分能力依赖任务栈地址获取，可能需要按 demo 修改 FreeRTOS 源码或适配相关接口。

结论

CmBacktrace 适合作为 Cortex-M 项目的故障诊断基础设施。它把 HardFault 和断言现场整理成日志，再通过 addr2line 把调用栈地址还原到源码位置。

学习它时重点看三件事：cmb_cfg.h 怎么匹配平台，HardFault 入口怎么把真实 LR/SP 交给库，构建产物怎么保留符号供 addr2line 使用。把这三件事打通后，很多偶发死机就可以从“只能复现调试”变成“日志可回收分析”。
