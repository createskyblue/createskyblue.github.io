# 串口接收为什么会丢数据：从轮询到循环缓冲的改造思路

串口接收看似只是“收到字节再读出来”，实际工程里会遇到短命令、连续数据流、主循环忙碌、协议解析耗时不稳定等情况。接收路径设计不好，就容易出现丢字节、乱序、短包延迟和偶发错包。

本文记录一种从简单接收到分层接收链路的演进思路。重点不在堆技术名词，重点在把硬件接收、DMA 搬运、中断触发、软件队列和用户层解析拆开，让每一层职责清楚、边界可测。

## 轮询：最小可用，但容易错过数据

> 快递站类比：最早的快递站没有提醒机制，老板只能反复去门口看有没有快递。快递很少时能工作；一旦老板在里面忙，门口来了几车快递，没人及时接收，包裹就可能丢掉。

轮询接收也是这个逻辑。主循环反复检查串口接收标志，发现有数据后读取数据寄存器。它足够直观，适合 bring-up、低速调试和最小可用验证。

轮询的问题来自 CPU 时间不可控。主循环可能正在处理其他任务，也可能被某段逻辑占住。只要轮询间隔变长，外设接收寄存器就可能来不及被读取，后续字节进入时触发溢出。

这个阶段的验证目标很简单：低波特率 Echo 必须稳定。如果低速都不稳定，应先检查引脚复用、波特率配置、串口时钟和基础读写路径。

## 字节中断：及时响应，但中断频率升高

> 快递站类比：给快递站装门铃后，老板不用反复去门口。快递员到了按铃，老板出来签收。快递少时很方便；高峰期门铃一直响，老板会被签收动作占满。

字节中断把“主循环反复查看”改成“数据来了再通知 CPU”。串口每收到一个字节触发一次中断，CPU 在中断服务函数里读出数据寄存器，丢字节风险比轮询低。

新边界是中断频率。波特率升高后，每个字节都触发一次中断，CPU 会被大量短中断压住。中断里只应该快速取走数据、放入轻量缓冲、退出。

协议解析、日志打印、大块内存复制都不适合放在字节中断里。这些动作会拉长中断时间，增加后续字节丢失风险，也会影响系统中其他任务的实时性。

这一阶段需要观察波特率提高后的系统表现。如果主循环明显变慢，或 Echo 在高频小包下开始跳字节，说明每字节中断已经接近可用边界。

## 普通 DMA：减少中断，但存在重启空档

DMA 是 direct memory access，也就是外设直接访问内存。普通 DMA 接收会准备一块 DMA buffer，让串口外设把收到的字节直接写入内存。

这样 CPU 不需要为每个字节进入中断，只需要等一块 buffer 写满后再处理。相比字节中断，普通 DMA 明显降低了中断压力，适合接收固定长度或接近固定长度的数据块。

问题出现在 DMA 完成后的衔接。普通 DMA 写满后，需要 CPU 处理当前 buffer，再重新启动下一次 DMA 接收。完成中断、回调处理、重新配置和启动 DMA 之间都可能形成接收空档。上位机持续发送时，新字节可能刚好落在这个空档里。

普通 DMA 还会让短包提交变慢。很多串口输入是变长数据，可能只发几个字节就停。如果驱动只等 buffer 写满，上层会长时间拿不到这段数据，表现为短命令延迟或偶发无响应。

这个阶段要验证两件事：连续输入时，DMA 完成到下一次启动之间不能丢字节；短包输入时，系统不能只等整块 buffer 写满才交给上层。

## 双缓冲：减少切换空档，但短包仍要提交

双缓冲使用 A、B 两块 buffer。DMA 当前写 A，A 满后切到 B，CPU 处理 A；B 满后再切回 A。接收和处理被拆开，一块接新数据，另一块交给 CPU。

它减少了普通 DMA 的重启空档，也让固定长度数据块更好处理。对音频采样、ADC 批量采样、固定帧长数据，这个模型很自然。

串口接收的麻烦在于数据通常是字节流。命令长短不固定，停顿位置也不固定。双缓冲仍然偏向“满块提交”，面对只收到几个字节就暂停的输入，还需要额外的提交时机。

双缓冲也不能突破消费速度限制。协议解析或业务处理长期慢于输入速度时，A、B 两块 buffer 最终都会被占住，后续数据仍会被覆盖或丢弃。

这一阶段重点检查 A/B 顺序、切换时机和短包提交。如果出现整块丢失、A/B 顺序颠倒、短包长时间不回显，说明状态管理或提交策略有问题。

## 空闲中断（IDLE）：让变长数据及时提交

空闲中断（IDLE）表示串口线上一段时间没有新字节进入。对变长串口数据来说，它提供了一个自然提交点：这一段输入暂时结束了，可以把 DMA 工作区里新增的数据交给后续软件层。

IDLE 的作用是提交数据，不负责解析协议。驱动层只需要根据 DMA 当前写位置和上次已处理位置计算新增范围，再把这段字节交出去。至于这些字节是否组成完整协议帧，应由上层解析器判断。

> 实现细节：常见驱动库会用 DMA 剩余计数换算当前写位置，例如 `buffer_size - dma_remaining_count`。这类代码只是在定位写指针，设计重点仍然是“IDLE 触发提交，后续软件层承接数据”。

IDLE 解决了普通 DMA 和双缓冲的短包问题。buffer 没满也可以提交，上层不需要等到整块 DMA buffer 写满。

它的限制也很直接：IDLE 依赖串口线空闲。如果上位机持续发送，中间没有足够长的停顿，IDLE 就不会及时触发。连续流场景需要固定搬运节点补位。

## 循环 DMA + HT/TC：补上连续流场景

循环 DMA 指 DMA 写到缓冲区末尾后自动回到开头继续写，形成环形接收区。它的价值是接收缓冲区不需要反复停止和重启，普通 DMA 的重启空档被拿掉。

> 快递站类比：循环 DMA 可以理解成一条循环传送带，FIFO 可以理解成后面的仓库。传送带持续接收包裹，仓库暂存已经搬下来的包裹，上层有空再慢慢分拣。

只靠 IDLE 仍然不够。连续数据流可能长时间没有空闲，所以需要半传输中断（HT）和传输完成中断（TC）作为固定搬运节点。HT 表示 DMA 写到缓冲区一半，TC 表示 DMA 写到缓冲区末尾。

IDLE、HT、TC 应该进入同一个搬运逻辑：读取当前 DMA 写位置，和上次已处理位置比较，计算新增数据范围，再交给后续软件层。没有回绕时，新增数据是一段连续内存；发生回绕时，需要拆成尾部和头部两段处理。

这个结构相当于把一块连续 DMA 内存虚拟成了乒乓缓冲。前半区、后半区分别由 HT 和 TC 提交；IDLE 负责补齐不满半区或不满整区的短包。接收链路既能处理持续流，也能处理断续短包。

循环 DMA 的边界在指针计算和覆盖风险。上次处理位置必须准确推进，回绕必须处理正确。用户层消费过慢时，DMA 写位置可能追上尚未处理的数据，这时必须暴露溢出或覆盖风险。

## 软件队列（FIFO）：解耦实时接收和协议解析

软件队列（FIFO）用于保存已经脱离 DMA 工作区、等待上层处理的数据。它承接循环 DMA 搬出来的字节流，让上层在自己的节奏里解析。

FIFO 的价值不只是“缓存更多数据”。更重要的是分层：DMA buffer 是硬件接收工作区，持续被 DMA 写；FIFO 是软件侧待处理字节流，面向协议解析和业务消费。

这条链路的职责可以拆成四层：

- DMA buffer 负责临时接住硬件输入。
- 中断处理负责在 IDLE、HT、TC 节点搬运新增字节。
- FIFO 负责保存有序字节流，并吸收短时间突发。
- 用户层负责协议解析、校验、组包、丢帧恢复等语义。

驱动层不应该解析协议，不应该替用户清理业务缓存，也不应该默认 FIFO 永远够用。FIFO 满了可以丢数据，但不能静默覆盖。

静默覆盖会把问题伪装成偶发错包、乱序或解析失败。溢出计数必须保留，至少要记录丢弃字节数和溢出次数。这样才能区分“驱动搬运错了”和“上层消费速度跟不上”。

这个阶段的验证重点是保序和可观测性。设计容量内，FIFO 只能带来排队延迟，不能带来乱序、重复或跳号；超过容量后，允许出现可观测丢弃，不能出现无记录的数据污染。

## 直接读取循环缓冲：省内存，但边界更紧

资源紧张时，可以取消独立 RX FIFO，直接把 DMA 循环缓冲封装成可读队列。这样少一次从 DMA buffer 到软件 FIFO 的内存搬运，也省掉一块 RAM。

这个做法成立有一个前提：DMA buffer 需要加长。它不再只是临时接收工作区，还承担“用户可读队列”的职责。传送带如果要兼任仓库，就必须足够长，能覆盖最坏消费延迟。

DMA 直读的基本模型是维护软件读指针和 DMA 写指针。可读长度由两者计算，读取函数按需取出任意字节数。没有回绕时直接读一段；发生回绕时先读尾部，再读头部。

最低要求包括：

- DMA buffer 要按最坏消费延迟加长，不能沿用很小的临时接收缓冲。
- 可读长度必须由 DMA 写位置和软件读位置计算。
- 读取函数必须处理回绕，不能假设数据连续。
- 写位置追上读位置时，必须判断覆盖风险。
- 溢出统计仍然必须保留，不能把覆盖伪装成随机错字节。

独立 FIFO 的职责边界更清楚，可观测性更好；DMA 直读更省搬运和 RAM，但读写指针、覆盖判断、缓冲区长度估算和压力测试要求更高。

## 发送侧队列：让多个模块按顺序发送

接收侧稳定后，发送侧也会遇到类似问题。多个模块可能同时要打印日志、发送协议帧或回显数据，但串口发送通道一次只能发送一段。

简单回显可以直接判断发送空闲后启动 DMA。模块变多后，调用方会被迫关心“现在能不能发”，发送冲突和覆盖风险会扩散到业务层。

发送侧队列可以把入口统一起来。外部模块只负责投递待发送数据；串口发送驱动在空闲时从 TX FIFO 取一段启动 DMA；发送完成中断清 busy 标志，再继续取下一段。

发送完成中断的职责要保持克制：推进下一段发送，更新状态，记录错误。它不应该处理复杂协议，也不应该在回调里做长时间阻塞操作。

接收侧 RX FIFO 和发送侧 TX FIFO 组合后，Echo 压测才能长期运行。PC 端持续发送随机流，设备从 RX FIFO 取数据，再经 TX FIFO 排队发回，两个方向都需要保序。

## Echo 压测：用外部结果验证链路可靠性

串口链路是否稳定，不能只看串口助手里“好像有回显”。Echo 压测的价值在于使用外部结果验证接收链路：PC 持续发送随机数据，设备原样回显，PC 端逐字节比较长度、内容和顺序。

PC 端至少需要检查：

- 发送字节数和回显字节数一致。
- 回显内容和发送内容一致。
- 字节顺序不乱。
- 不重复，不跳号。
- 设备持续运行，发送完成回调能继续推进。

测试场景可以分层推进：

- 固定长度短包：验证基础收发、中断入口和发送完成回调。
- 随机长度包：覆盖变长数据、IDLE 提交和 DMA 批量搬运。
- 连续随机流：减少空闲时间，验证 HT/TC 是否能持续推进搬运。
- 逐步提高波特率：观察系统从稳定到接近极限的过程。
- 加入主循环负载：验证用户处理变慢时 FIFO 是否能吸收短时间突发。

正常压力下不能丢、不能乱序、不能重复。超过设计容量时可以丢，但必须有溢出计数。测试报告要区分“设计范围内失败”和“压力越界后的可观测丢弃”。

随机流压测会打破“刚好按包发送”的理想条件。真实系统里，上位机可能连续发送，也可能短包密集出现，还可能在任意位置停顿。随机长度、随机内容、逐步提高波特率，能更早暴露指针推进、回绕处理、队列满处理和发送完成衔接中的边界错误。

## 适用边界：缓冲容量有上限

`循环 DMA + IDLE + HT/TC + FIFO` 适合做通用串口接收底座，特别适合变长数据、突发输入和上层处理时间不稳定的场景。

它仍有容量上限。缓冲只能吸收短时间速率不匹配，不能解决长期输入速度大于消费速度的问题。

需要提前确认这些边界：

- FIFO 满时仍然会丢数据，工程上需要统计并暴露这个事件。
- 驱动层只搬运字节，不替协议层判断帧边界和恢复策略。
- DMA buffer 太小会增加 HT/TC 中断频率，太大会占用更多 RAM。
- 取消独立 RX FIFO 后，DMA buffer 还要承担队列职责，长度必须按最坏消费延迟估算。
- 用户层长期消费不足时，最终要靠流控、限速或协议重试解决。

不同 MCU、DMA 控制器和串口外设的行为会有差异，实际工程中仍需要结合芯片手册、驱动库实现和压力测试结果确认边界。
