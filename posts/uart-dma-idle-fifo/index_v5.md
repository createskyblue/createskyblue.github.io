# 串口接收为什么会丢数据：从轮询到循环缓冲的改造思路

串口接收是嵌入式系统的基本输入路径。本文记录如何将一个简单的轮询接收，逐步演进为循环 DMA、空闲中断、固定搬运节点和软件队列组成的解耦架构，并保证每一层演进都有明确的压力测试边界。

串口接收看似只是“收到字节再读出来”，实际工程里会遇到短命令、连续数据流、主循环忙碌、协议解析耗时不稳定等情况。接收路径设计不好，就容易出现丢字节、乱序、短包延迟和偶发错包。

这条改造路线不追求堆叠复杂技术，重点是把硬件接收、DMA 搬运、中断触发、软件队列和用户层解析拆开。每一层只处理自己的职责，每一层都能被外部压测验证。

## 轮询：最小可用，但容易错过数据

### 【快递站类比】

最早的快递站没有提醒机制。老板每隔几分钟跑到门口看一眼，有快递就拿进来，没有快递就回去做别的事。

快递很少时，这个办法能工作。老板一旦在里面忙，门口来了好几车快递，没人及时接收，包裹就可能丢掉。

### 【技术解耦与实现】

轮询就是主循环反复检查接收标志，发现有数据后读取数据寄存器。它的优点是直观，适合 bring-up、低速调试和最小可用验证。

问题在于 CPU 的主循环不可能长期只服务接收寄存器。只要轮询间隔变长，外设接收寄存器就可能来不及被读取，后续字节进入时触发溢出。

轮询不适合作为高负载接收路径。这个阶段只需要做最小验证：低波特率 Echo 如果都不稳定，应先检查串口配置、引脚复用和基础读写路径。

## 字节中断：及时响应，但中断频率升高

### 【快递站类比】

快递站在门口装了门铃。快递员到了按门铃，老板出来签收，不需要反复去门口查看。

快递少时很方便。高峰期门铃一直响，老板只顾着签收，里面的分拣和记账都做不动。

### 【技术解耦与实现】

字节中断把“主循环反复查看”的方式改成“数据来了再通知 CPU”。串口收到一个字节后触发中断，CPU 在中断服务函数里读出数据寄存器。

限制来自中断频率。波特率升高后，每个字节都触发一次中断，CPU 会被大量小中断压住。中断里只应该做最小动作：快速取走数据、放入轻量缓冲、退出。

协议解析、打印、大块复制都不应该放到字节中断里。它们会拉长中断时间，增加后续字节丢失风险，也会影响系统中其他任务的实时性。

这一阶段重点观察中断频率上升后的系统表现。波特率提高后，如果主循环明显被拖慢，说明每字节中断已经接近边界。

## 普通 DMA：减少中断，但存在重启空档

### 【快递站类比】

快递站在门口放了一个大箩筐。快递员不用按门铃，也不用等老板，直接把包裹放进箩筐。

箩筐满了，老板再一次性搬进去。老板不用每个包裹都跑一趟，但搬箩筐、倒空、放回门口的间隔里，新来的快递又没地方放。

### 【技术解耦与实现】

DMA 是 direct memory access，也就是外设直接访问内存。普通 DMA 接收会准备一块接收缓冲区，让串口外设把收到的字节直接搬到内存。

这样 CPU 不需要为每个字节进入中断，只需要等一块 DMA buffer 写满后再处理。这个结构减少了中断压力，但也引入了新的边界：DMA 写满后需要处理这段内存，然后重新启动下一次 DMA 接收。

重启期间可能出现接收空档。如果上位机连续发送，DMA 完成、CPU 处理、重新启动接收之间的时间都可能让新字节没有地方进入。

普通 DMA 还有短包问题。很多串口数据长度不固定，可能只发几个字节就停了。如果只等 DMA buffer 写满，短包会迟迟不提交给上层。

这一阶段重点检查两类新增风险：只处理满 buffer，短包一直等不到处理；DMA 完成后重启太慢，连续输入时出现空档。

## 双缓冲：减少切换空档，但短包仍要提交

### 【快递站类比】

快递站放了两个箩筐。A 箩筐满了，老板搬 A；快递员马上改往 B 箩筐里放包裹。B 满了，再切回 A。

这个办法减少了门口没地方放快递的时间。但如果快递员只放了两个包裹就走了，箩筐没满，老板可能一直等着“满了再搬”。

### 【技术解耦与实现】

双缓冲区通常使用 A、B 两块 buffer。DMA 当前写 buffer A，A 满后切到 buffer B，CPU 处理 A；B 满后再切回 A。

这个模型可以减少普通 DMA 的重启空档。接收和处理被拆开：一块 buffer 接收新数据，另一块 buffer 交给 CPU 处理。

双缓冲适合固定长度数据块。它仍然没有解决变长数据。串口经常是字节流，一段命令发完后，buffer 不一定刚好填满。系统需要在未填满时也能提交已有数据。

双缓冲还受上层消费速度限制。如果协议解析或业务处理长期慢于输入速度，两块 buffer 最终都会被占住，后续数据仍会被覆盖或丢弃。

这一阶段重点检查 A/B 切换顺序和未填满 buffer 的提交时机。出现整块丢失、A/B 顺序颠倒或短包长时间不回显，都说明双缓冲状态管理还有问题。

## 空闲中断：让变长数据及时提交

### 【快递站类比】

快递站在门口加了一个感应器。快递员放完这一波包裹离开后，门口安静下来，感应器通知老板来搬。

这样不管箩筐有没有满，只要这一波快递暂时结束，老板就能把已有包裹搬进去。

### 【技术解耦与实现】

空闲中断（IDLE）用于识别串口线上一段时间没有新字节进入。对变长数据来说，它提供了一个很重要的提交时机：这一段输入暂时结束了，可以把 DMA 工作区里已经收到的数据搬走。

空闲中断不负责解析协议，也不判断这一段是否完整业务帧。它只解决一个底层问题：DMA buffer 里有一段新增字节，现在可以提交给后面的软件层。

实现上，驱动通过 DMA 当前写入位置和上次已处理位置，计算新增范围，再把这段数据搬到后续队列。

> 实现细节：常见驱动库会用 DMA 剩余计数换算写指针，例如 `buffer_size - dma_remaining_count`。这个代码只是在定位写位置，核心设计仍然是“空闲中断触发搬运，后续软件层承接数据”。

空闲中断的限制也很明确：它依赖“空闲”。如果上位机连续发送，没有足够长的停顿，空闲中断就不会及时触发。持续流输入需要固定搬运节点。

## 循环缓冲：让连续输入不必停下来等待

### 【快递站类比】

快递站把两个箩筐换成了一条循环传送带。快递员不停往传送带上放包裹，传送带走到一半提醒搬一段，走到末尾再提醒搬一段。

如果快递员放一会儿就走，门口感应器也会提醒老板搬走当前已有包裹。连续快递和零散快递都能被及时处理。

### 【技术解耦与实现】

循环 DMA 指 DMA 写到缓冲区末尾后自动回到开头继续写，形成环形接收区。它省掉了普通 DMA 反复停止和重启的空档，也省掉了显式 A/B 双缓冲状态。

仅靠空闲中断不够，因为持续流可能长时间没有空闲。因此循环 DMA 通常配合两个固定搬运节点：

- 半传输中断（HT）：DMA 写到缓冲区一半时触发。
- 传输完成中断（TC）：DMA 写到缓冲区末尾时触发。

空闲中断、半传输中断和传输完成中断都进入同一个搬运逻辑：计算从上次处理位置到当前位置之间新增了哪些字节，把它们交给后面的软件层。

> 实现细节：在常见驱动库里，通常会启用半传输和传输完成事件，再让 DMA 中断和串口空闲中断走同一个“计算新增范围并搬运”的函数。函数名不重要，职责必须统一。

循环缓冲的核心是维护两个位置：上次已处理位置和当前 DMA 写入位置。数据没有回绕时，新增数据是一段连续内存；数据发生回绕时，需要拆成尾部和头部两段处理。

这一阶段重点检查连续输入。串口线上长时间没有空闲时，半传输和传输完成中断必须能按固定节点推进搬运。

## 软件队列：解耦实时接收和协议解析

### 【快递站类比】

传送带负责接包裹，后面的仓库负责暂存包裹。业务部门有空时再去仓库分拣。

即使业务部门临时忙，前面的接收链路也能先把包裹囤住，不至于门口丢件。

### 【技术解耦与实现】

软件队列（FIFO）用于保存已经从 DMA 工作区搬出来、等待上层处理的数据。它的价值超过了“缓存更多数据”，真正承担的是实时接收和业务解析之间的解耦。

DMA buffer 是硬件接收工作区，容量通常较小，且持续被 DMA 写。软件队列是上层还没来得及处理的数据仓库，容量可以按业务压力配置。

这条边界很重要：

- DMA buffer 负责临时接住硬件输入。
- 中断处理负责按空闲、半传输、传输完成节点把新增字节搬走。
- 软件队列负责保存有序字节流，并吸收短时间突发。
- 用户层负责协议解析、校验、组包、丢帧恢复等语义。

驱动层不应该解析协议，不应该替用户清理业务缓存，也不应该假装软件队列永远够用。队列满时必须累计丢弃字节数和队列溢出次数。

静默覆盖会把问题伪装成偶发错包、乱序或解析失败。溢出计数能把“用户消费速度跟不上”暴露出来，这是后续定位问题的基础。

这一阶段重点检查保序和可观测性。容量没有越界时，软件队列只能带来排队延迟，不能带来乱序、重复或跳号；容量越界时，必须有溢出计数。

## 直接读取循环缓冲：省内存，但边界更紧

### 【快递站类比】

如果不想再租后面的仓库，可以把循环传送带加长，让传送带自己承担临时仓库职责。

这样能省掉“从传送带搬到仓库”的动作，但业务部门必须及时从传送带上拿包裹。拿慢了，传送带转一圈，新包裹会盖掉旧包裹。

### 【技术解耦与实现】

有些资源紧张的场景，可以取消独立软件队列，直接把 DMA 循环缓冲封装成可读队列。

这个做法不能只“拆仓库”。如果取消独立队列，DMA 缓冲区本身就要承担临时仓库职责，因此需要把循环 DMA buffer 配得足够大。

这个设计少一次从 DMA buffer 到软件队列的内存搬运，也省掉一块独立 RAM。代价是 DMA buffer 同时承担两个职责：硬件接收工作区和用户可读队列。读写边界更紧。

最低要求包括：

- DMA buffer 要按最坏消费延迟加长，不能沿用很小的临时接收缓冲。
- 可读长度必须由 DMA 写位置和软件读位置计算。
- 读取函数必须处理回绕，不能假设数据连续。
- 写位置追上读位置时，必须判断覆盖风险。
- 溢出统计必须保留，不能把覆盖伪装成随机错字节。

外部软件队列和加长 DMA buffer 后直接读取没有绝对高低。外部软件队列的职责边界更清楚，可观测性更好；DMA 直读更省搬运和 RAM，但读写指针、覆盖判断、缓冲区长度估算和压力测试都要更严谨。

## 发送侧队列：让多个模块按顺序发送

### 【快递站类比】

收快递解决后，发快递也有类似问题。多个部门都想把包裹交给门口的车，但一辆车一次只能装一批。

更稳的做法是先排队。车空了就装下一批，装完再发下一批。

### 【技术解耦与实现】

接收侧解决后，发送侧也会遇到类似问题。多个模块都想打印日志或发送协议帧，但串口只有一条发送通道，一次只能发送一段数据。

发送侧通常会有 busy 标志，并在发送完成回调里清除。简单回显可以直接判断空闲后启动 DMA 发送，但多个模块同时发送时，调用方会被迫关心“现在能不能发”。

发送侧队列可以把发送入口统一起来：外部模块只写入待发送数据，串口发送驱动在空闲时从队列取一段启动 DMA，发送完成中断清 busy 并继续取下一段。

这样发送侧也形成同样边界：用户只负责投递，驱动负责按串口单通道特性串行发出。

这一阶段重点检查接收队列和发送队列的组合状态。PC 端看到的仍然应该是原始随机流，顺序不能乱，内容不能变，两个 DMA 通道的状态不能互相破坏。

## Echo 压测：用外部结果验证链路可靠性

### 【快递站类比】

检查快递站是否靠谱，不能只看“门口有人收件”。更可靠的办法是给每个包裹编号，发出去多少、收回来多少、顺序有没有乱，都要核对。

如果快递量超过仓库容量，允许出现丢件，但必须能从记录里看出来，不能装作一切正常。

### 【技术解耦与实现】

每一层优化都应该接受同一个外部判据：PC 端持续发送随机数据，设备原样回显，PC 端负责校验。测试目标不能只看“有没有回显”。

PC 端需要逐字节比较：

- 发送字节数和回显字节数一致。
- 回显内容和发送内容一致。
- 字节顺序不乱。
- 不重复，不跳号。
- 设备持续运行，发送完成回调能继续推进。

推荐测试分成几组：

- 固定长度短包：验证基础收发和中断入口。
- 随机长度包：覆盖变长数据和 DMA 批量搬运。
- 连续随机流：减少空闲时间，验证固定搬运节点是否有效。
- 逐步提高波特率：观察系统从稳定到接近极限的过程。
- 加入主循环负载：验证用户处理变慢时软件队列是否能吸收短时间突发。

正常压力下不能丢、不能乱序、不能重复。超过设计容量时可以丢，但必须有溢出计数。测试报告要区分“设计范围内失败”和“压力越界后的可观测丢弃”。

随机流压测会打破“刚好按包发送”的理想条件。真实系统里，上位机可能连续发送，也可能短包密集出现，还可能在任意位置停顿。随机长度、随机内容、逐步提高波特率，能更早暴露边界错误。

## 适用边界：缓冲容量有上限

### 【快递站类比】

快递站加传送带、加仓库，只能提高吞吐和缓冲能力。仓库面积仍然有限。

如果快递长期进得比出得快，最终还是会堆满。区别在于系统要能记录“什么时候满了、丢了多少”，不能让丢件变成猜谜。

### 【技术解耦与实现】

`循环 DMA + 空闲中断 + 半传输 / 传输完成中断 + 软件队列` 适合做通用串口接收底座，特别适合变长数据、突发输入和上层处理时间不稳定的场景。

它仍有容量上限：

- 软件队列满时仍然会丢数据，工程需要统计并暴露这个事件。
- 驱动层只搬运字节，不替协议层判断帧边界和恢复策略。
- DMA 缓冲区太小会增加半传输 / 传输完成中断频率；如果取消独立软件队列，DMA 缓冲区还要承担仓库职责，长度必须按最坏消费延迟估算。
- 用户层长期消费不足时，任何缓冲都会被填满，最终必须靠流控、限速或协议重试解决。

不同 MCU、DMA 控制器和串口外设的行为会有差异，实际工程中仍需要结合芯片手册、驱动库实现和压力测试结果确认边界。
