# 串口接收从轮询演进到 DMA 循环缓冲和 FIFO 解耦

串口收发看起来只是读写一个外设，实际会很快遇到三个问题：CPU 不能一直等串口，接收数据没有天然包边界，上层处理速度也不一定跟得上输入速度。

在很多 ARM Cortex-M MCU 上，USART、DMA、IDLE 中断、半传输中断和传输完成中断都是常见外设能力。本文讨论的是这一类芯片上通用的接收结构：`USART + DMA circular + IDLE + HT/TC + FIFO`。DMA 负责把字节先接住，中断负责在合适的时间把 DMA 缓冲区里已经到达的数据搬走，FIFO 负责把驱动层和用户处理层解耦。发送侧也可以按同样思路加一个 TX FIFO，让外部只负责投递待发送数据。

## 从轮询寄存器开始

最朴素的串口接收是轮询状态寄存器。主循环反复检查 RXNE 之类的接收标志，发现有数据后读取数据寄存器。

这个流程最容易理解：

- 外设收到一个字节。
- 状态位提示 CPU 可以读。
- CPU 读取数据寄存器，拿到这个字节。

它的问题也很直接。主循环如果在做别的事情，轮询间隔就会变长。串口持续输入时，CPU 读慢了，外设接收寄存器可能被后续字节覆盖，最终触发溢出。轮询适合 bring-up、低速调试和极简单场景，不适合做成通用串口接收底座。

这个阶段可以先用 Echo 做最小验证。PC 端持续发送随机字节，设备收到什么就回什么，PC 端把回显内容和发送序列逐字节比较。低波特率下如果都不能稳定回显，先不要引入 DMA 或 FIFO，问题还在最基础的串口配置、引脚复用或寄存器读取路径。

## 用中断减少等待

下一步通常是打开串口接收中断。CPU 不再主动反复检查串口，外设收到字节后触发中断，在中断服务函数里读取数据寄存器。

中断把“等待数据”的成本降下来了，但每个字节仍然要进一次中断。波特率升高后，中断频率会直接压到 CPU 上。中断里如果还做协议解析、打印、复制大块数据，接收路径就会变成系统抖动源。

所以中断接收的核心边界是：中断只适合快速拿走字节，不能承担复杂处理。要让接收路径稳定，还需要把“外设搬运”和“业务消费”分开。

验证方式仍然沿用 Echo。区别是这次要逐步提高波特率，并让主循环同时做一些轻量任务，例如 LED 翻转或周期打印。可靠性不看“肉眼看到有回显”，要看 PC 端校验结果：回显长度一致、内容一致、顺序一致、设备没有卡死。只要随机流开始出现缺字节或乱序，就说明每字节中断路径已经接近边界。

## 加 DMA 接住连续字节

DMA 的作用是让外设直接把收到的字节搬到内存。CPU 不需要每个字节进一次中断，只要在一段数据到达后再处理内存里的缓冲区。

第一版可以先用普通 DMA：准备一块固定 RX buffer，启动一次外设到内存的 DMA 接收。DMA 写满这块 buffer 后触发完成中断，CPU 再处理这段内存，然后重新启动下一次 DMA 接收。

这里已经出现了一个关键变化：接收缓冲区不再是用户直接消费的数据队列。它只是 DMA 正在写的临时工作区。用户如果直接慢慢读这个工作区，会和 DMA 写入动作冲突，也无法稳定表达“哪些字节已经交给上层，哪些字节还没处理”。

DMA 版本的 Echo 测试要额外关注批量边界。PC 端随机生成不同长度的数据块，故意覆盖短包、长包、贴近 DMA 缓冲区大小的包，再检查回显字节流是否完全一致。这个测试可以暴露两个典型错误：只处理了一次 DMA 完成，没有处理未填满的短包；DMA 完成后重启太慢，中间输入字节落在接收空档里。

## 普通 DMA 加双缓冲区

普通 DMA 的问题在于“处理”和“接收”抢同一块 buffer。DMA 写满后，CPU 要处理这块内存；如果这时重新启动接收太晚，串口仍然可能有新字节进来。

一个自然改进是双缓冲区，也就是常说的乒乓缓冲：

- DMA 当前写入 buffer A。
- buffer A 满后触发完成中断。
- 驱动马上切到 buffer B 继续接收。
- CPU 在后台处理 buffer A。
- buffer B 满后再切回 buffer A。

这样接收和处理可以并行推进。DMA 永远有一块 buffer 可写，CPU 处理另一块已经填好的 buffer。对固定长度数据块来说，这个模型很直观。

双缓冲区仍然有两个边界。第一，串口数据常常是变长的，buffer 没填满时也需要知道“当前这一段可以处理了”，所以 IDLE 中断开始变得有价值。第二，CPU 如果处理速度长期低于输入速度，两块 buffer 迟早都会被占住，后续数据仍会覆盖或丢失。

这个阶段的 Echo 测试要覆盖两类输入：一类是刚好填满 buffer 的连续块，用来验证 A/B 切换；另一类是不同长度的短包，用来验证 IDLE 或超时机制能否把未填满的 buffer 及时交给上层。逐步提高波特率后，如果开始出现整块丢失或 A/B 顺序颠倒，说明双缓冲状态切换还有问题。

## DMA 缓冲区满了还要搬走

只加 DMA 和双缓冲区还不够。DMA 缓冲区本质上仍然有限。即使用了两块 buffer，如果输入速度很快，上层又没有及时处理，两块 buffer 也会被填满。

这时需要一个更大的、由用户层消费的 FIFO。DMA 缓冲区只负责短时间接住硬件输入，FIFO 负责保存已经从 DMA 工作区搬出来、等待用户处理的数据。

驱动层可以只依赖两个队列操作：写入一段字节、查询剩余空间。这样它只知道“有一个队列可以写”，不需要知道上层最终是回显、解析协议，还是交给其他任务。

这个边界很重要：

- DMA buffer：硬件接收工作区，容量小，持续被 DMA 写。
- RX FIFO：软件缓冲队列，容量相对大，给用户层按自己的节奏读。
- 用户逻辑：从 FIFO 取数据，决定回显、组包、解析或丢弃。

如果 FIFO 空间不够，驱动应该累计丢弃字节数和队列溢出次数。这比静默覆盖要好，至少能把消费速度不足暴露出来。

引入 FIFO 后，Echo 测试的目标从“DMA 能不能收到”变成“接收和消费速度解耦后是否仍然保序”。PC 端持续发送随机流，设备主循环从 FIFO 取一小段再用 DMA 发回。这个测试可以故意让读取块大小小于输入突发长度。如果 FIFO 边界处理正确，回显只会有可解释的排队延迟，不应该出现字节交换、重复或跳号。FIFO 满时允许测试判定为压力超过设计容量，但必须能看到溢出计数增长，不能静默错。

## IDLE 中断负责处理变长数据

串口是字节流，硬件不知道一包数据从哪里开始、到哪里结束。DMA 只会持续搬字节，也不会告诉上层“这批数据已经停了”。

IDLE 中断用来捕捉一段接收空闲。对很多命令式串口协议来说，一段数据发完后总会有短暂停顿，IDLE 就可以作为“该把当前已经收到的数据搬走”的触发点。

驱动初始化时清 IDLE 标志并打开 `UART_IT_IDLE`。IDLE 中断进入后，驱动通过 DMA 剩余计数反推出当前写入位置：

```c
uint32_t thisCount = USART_DMA_BUFFER_SIZE - __HAL_DMA_GET_COUNTER(ctx->hdma);
```

然后用一个软件位置记录上次已经搬走的位置。新写入位置在旧位置之后时，新增数据是一段连续内存；新写入位置回到旧位置之前时，说明 DMA 写指针绕回了缓冲区开头，需要拆成尾部和头部两段搬进 FIFO。

这个设计让 IDLE 中断不用关心协议包格式，只负责把 DMA 工作区里“新到达且还没搬走”的字节交给 FIFO。

## 循环 DMA 只靠 IDLE 会漏掉持续流

IDLE 有一个前提：串口线上出现空闲。如果上位机连续发数据，中间没有足够长的停顿，IDLE 中断就不会及时触发。

普通 DMA 加双缓冲区能解决处理期间的接收空档，但仍然要维护 A/B 状态，并在每次完成中断后切换或重启接收。循环 DMA 把这件事交给 DMA 自己做：DMA 写到末尾后自动绕回开头继续写。这个模式省掉了显式乒乓缓冲区和反复重启 DMA 的空档，但也带来一个要求：驱动必须在 DMA 覆盖旧数据前把已接收数据搬走。

所以循环 DMA 通常要打开 DMA 半传输中断和传输完成中断：

```c
__HAL_DMA_ENABLE_IT(ctx->hdma, DMA_IT_TC | DMA_IT_HT);
```

DMA 中断和 USART IDLE 中断都调用同一个搬运函数。这样有三类触发点：

- IDLE：一段数据停下来，适合处理短包、变长包。
- HT：DMA 写到缓冲区一半，及时搬走前半段。
- TC：DMA 写到缓冲区末尾，及时搬走后半段。

HT/TC 相当于把一段连续的循环内存切成两个稳定观察点。物理上仍然只有一个 DMA 环形缓冲区，逻辑上获得了类似乒乓缓冲区的效果：前半区写满后搬一次，后半区写满后再搬一次，DMA 继续循环写。

这一层最需要持续流测试。PC 端不要只发一帧一停的短包，要连续发送随机数据，让串口线上尽量少出现空闲。测试从保守波特率开始，逐步提高到目标波特率，再继续加压一档。判据仍然是回显序列完全一致，外加 DMA/FIFO 统计值可解释：正常容量内不应增长丢弃计数，超过消费能力时应记录溢出。

如果只开 IDLE，这个测试会暴露问题：持续流没有空闲，驱动迟迟不搬 DMA 缓冲区，循环写指针最终覆盖未处理数据。加上 HT/TC 后，即使没有 IDLE，半缓冲和整缓冲两个节点也会定期触发搬运。

## FIFO 是驱动和用户代码之间的边界

把数据搬进 FIFO 后，串口接收驱动的职责就结束了。它不解析协议，不决定包是否有效，也不替用户清理缓存。它只保证尽量把硬件输入转换成顺序字节流，并暴露溢出统计。

用户侧使用方式很直接：检查 FIFO 里是否有数据，有数据且发送 DMA 空闲时，从 FIFO 读一段，再调用 DMA 发送回显。

这只是演示用法。换成真实协议时，用户层可以按自己的节奏从 FIFO 读取：

- 一次读一个字节喂给状态机。
- 一次读一段做帧解析。
- 先缓存到协议层，再按校验和长度决定是否提交。

FIFO 的意义超过了“再加一个缓存”。它把实时接收和业务处理分成两种速度：硬件来的时候先接住，业务有空再消费。只要平均消费速度跟得上输入速度，短时间突发就不会直接冲击上层。

## 发送侧也可以用 FIFO

发送侧通常会有一个 busy 标志，并在发送完成回调里清除。主循环回显时，只有发送 DMA 空闲才启动下一次发送。

这能演示 DMA 发送，但用户层仍然要关心“现在能不能发”。如果多个模块都想打印或发送协议帧，就容易出现忙等、丢包、互相抢发送入口的问题。

同样可以给发送侧加一个 TX FIFO：

- 外部模块只把待发送字节写入 TX FIFO。
- 串口发送驱动发现当前不忙，就从 TX FIFO 取一段启动 DMA。
- DMA 发送完成中断清 busy，并继续尝试发送下一段。

这样发送侧也形成同样的边界：用户只负责投递，驱动负责按串口的单通道特性串行发出。RX FIFO 解决“来得太快先接住”，TX FIFO 解决“要发的太多先排队”。

发送 FIFO 的验证也可以复用 Echo 思路。上层只把待回显数据写入 TX FIFO，发送驱动在 DMA 完成中断后继续取下一段。PC 端看到的仍然应该是原始随机流。这样可以同时验证 RX FIFO 的保序、TX FIFO 的保序，以及两个 DMA 通道在持续收发时不会互相破坏状态。

## 也可以去掉外部 RX FIFO

走到 `DMA circular + FIFO` 以后，还可以继续收缩结构。循环 DMA 缓冲区本身就是一段环形内存：DMA 写指针一直向前走，走到末尾再回到开头。只要再维护一个软件读指针，这段 DMA buffer 就可以直接封装成 FIFO。

这个封装的核心是两个位置：

- 写位置：由 DMA 剩余计数换算得到，也就是当前 `thisCount`。
- 读位置：由驱动维护，表示用户已经读到哪里。

用户调用读取函数时，驱动比较写位置和读位置，算出当前可读字节数。线性区域可以直接复制；遇到缓冲区尾部就拆成两段复制。读完后推进读位置。这样外部看到的是“读任意长度字节流”的接口，内部仍然只有一个循环 DMA 缓冲区。

这个做法可以砍掉外部 RX FIFO，优点是少一次搬运，也少一块 RAM。代价是 DMA buffer 需要承担两种职责：既是硬件接收工作区，也是用户可读队列。它必须足够大，并且必须能判断覆盖风险。

最小边界是：

- 可读长度必须由 DMA 写位置和软件读位置计算，不能直接按包长猜。
- 读函数要处理回绕，不能假设数据总是连续。
- 写位置追上读位置时，说明用户读得太慢，旧数据已经有被覆盖的风险。
- 需要保留溢出统计，否则问题会变成“Echo 偶发错字节”。

这种结构适合 RAM 很紧、接收处理足够快、驱动接口可以被统一封装的工程。外部 FIFO 适合把 DMA 工作区和用户消费队列分开，调试和职责边界更直观。两者的差异主要在内存、复杂度和可观测性。

## 用 Echo 压测作为演进判据

每一层优化都应该有同一个外部判据：PC 端持续发送随机数据，设备原样回显，PC 端负责校验。这样测试目标不会随着实现变化被稀释。

推荐把测试拆成几组：

- 固定长度短包：验证基础收发和中断入口。
- 随机长度包：覆盖变长数据和 DMA 批量搬运。
- 连续随机流：减少空闲时间，验证 HT/TC 能否替代单纯 IDLE。
- 逐步提高波特率：观察系统从稳定到接近极限的过程。
- 加入主循环负载：验证用户处理变慢时 FIFO 是否能吸收短时间突发。

通过标准也要明确：

- PC 端发送字节数和回显字节数一致。
- 回显内容和发送内容逐字节一致。
- 字节顺序不乱，不重复，不跳号。
- 设备不中断运行，发送完成回调能持续推进。
- 正常压力下队列溢出计数不增长。
- 超过设计容量时，溢出计数增长，测试报告明确标记为压力越界。

这套测试不能证明所有协议都可靠，但能证明底层字节通道可靠。只有 Echo 随机流稳定了，上层再谈帧格式、校验、重试和业务语义才有意义。

## 这个结构的适用边界

`DMA circular + IDLE + HT/TC + FIFO` 适合做通用串口接收底座，特别适合变长数据、突发输入和上层处理时间不稳定的场景。

它仍有容量上限。必须接受几个边界：

- FIFO 满时仍然会丢数据，工程需要统计并暴露这个事件。
- 驱动层只搬运字节，不替协议层判断帧边界和恢复策略。
- DMA 缓冲区太小会增加 HT/TC 中断频率，太大又会推迟数据进入 FIFO。
- 用户层长期消费不足时，任何缓冲都会被填满，最终必须靠流控、限速或协议重试解决。

这套设计的核心价值包含 DMA 搬运，也包含清楚的接收链路分层：硬件用 DMA 快速落内存，中断用 IDLE/HT/TC 找搬运时机，FIFO 保存已经脱离 DMA 工作区的数据，用户层按自己的协议节奏处理。
